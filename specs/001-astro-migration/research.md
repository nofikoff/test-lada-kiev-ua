# Research: миграция lada.kiev.ua на статическую генерацию

**Дата**: 2026-09-06 | **Фича**: [spec.md](./spec.md)

Все версии и поведение фреймворка проверены по документации Astro и npm 2026-09-06. Утверждения, взятые из общих знаний и не подтверждённые источником, помечены явно.

## R1. Фреймворк и версия

**Решение**: Astro 7.3.1, `output: 'static'`.

**Обоснование**: покрывает все три цели одним механизмом — статическая генерация даёт HTML с контентом, островная модель позволяет не грузить фреймворк вообще, Content Collections закрывают требование «контент как данные» с валидацией на сборке. Node 22.17.1 в системе удовлетворяет требованию Astro `node >= 22.12.0` (проверено `npm view astro@7.3.1 engines`).

**Альтернативы**:

- Оставить Vite + React и добавить пререндеринг (`vite-plugin-ssr`, `react-snap`): даёт HTML, но сохраняет 224 КБ рантайма и не решает ни данные, ни картинки, ни i18n-маршрутизацию.
- Next.js со статическим экспортом: закрывает те же задачи, но приносит React обратно как обязательную зависимость — прямо против выбранной цели.
- Eleventy/Hugo: легче Astro, но не дают ни типизированных коллекций с валидацией, ни встроенной оптимизации изображений; часть требований пришлось бы закрывать самописными скриптами.

## R2. Маршрутизация языковых версий

**Решение**: `i18n: { defaultLocale: 'uk', locales: ['uk','ru','en'], routing: { prefixDefaultLocale: false } }` плюс физические каталоги страниц `src/pages/`, `src/pages/ru/`, `src/pages/en/`.

**Обоснование**: `prefixDefaultLocale: false` — ровно действующая схема адресов: основной язык на корне, остальные с префиксом (подтверждено `reference/configuration-reference.mdx`). Конфигурация i18n не создаёт страницы сама, она задаёт поведение и даёт `Astro.currentLocale` и хелперы построения ссылок; страницы создаются файлами. Каталоги локалей выбраны вместо динамического `[lang]`, потому что при `prefixDefaultLocale: false` основной язык всё равно живёт отдельным файлом, и динамический параметр дал бы две разные механики для трёх одинаковых по смыслу страниц.

**Ключевое следствие для приёмки**: `build.format: 'directory'` (значение по умолчанию) выдаёт `ru/index.html`. Apache с включённым `DirectorySlash` отвечает на действующий адрес `/ru` перенаправлением 301 на `/ru/`. Адрес не теряется, вес ссылки передаётся, но канонический адрес обязан указывать на форму со слешем — иначе канонический адрес и фактический разойдутся.

**Альтернатива**: `build.format: 'file'` даёт `ru.html`; обслуживание адреса `/ru` тогда требует `MultiViews` или правил перезаписи, то есть переносит корректность адресов в конфигурацию сервера. Отклонено.

## R3. Код украинского языка

**Решение**: внутренний код `uk` вместо действующего `ua`. Адреса не меняются.

**Обоснование**: `uk` — код языка по ISO 639-1, `ua` — код страны по ISO 3166-1. Атрибут языка документа и указания языковых альтернатив требуют кода языка; действующая разметка `index.html` уже пишет `lang="uk"`, тогда как код в приложении — `'ua'`, то есть источник и разметка сегодня расходятся. В карте сайта локали объявляются полными тегами: `uk-UA`, `ru-UA`, `en`.

## R4. Хранение прайса

**Решение**: `src/data/prices.json` — массив объектов, у каждого явный `id`; загрузка через `file()` loader, схема на zod.

**Обоснование**: `file()` требует уникального идентификатора у каждой записи — либо поле `id` в массиве, либо ключ объекта (подтверждено `guides/content-collections.mdx`). Массив с явным `id` выбран потому, что порядок позиций в файле становится порядком отображения и виден при чтении, тогда как в объекте-карте порядок ключей — неявная договорённость.

Одно измерение данных обслуживает две группировки: поле `category` определяет страницу услуги, поле `group` — блок внутри перечня. Состав вкладок главной страницы задаётся отдельной конфигурацией, перечисляющей группы, и не хранит ни одной позиции — поэтому вкладки и страницы категорий не могут разойтись.

**Альтернативы**:

- Три файла по языкам (`prices.uk.json` и т.д.): списки позиций в разных языках могут разъехаться по составу, а не только по переводу. Отклонено.
- Отдельная коллекция под каждую категорию через `parser`: возможно (документация показывает извлечение нескольких коллекций из одного файла), но добавляет четыре определения там, где хватает одного поля.

## R5. Тексты страниц категорий

**Решение**: `src/content/services/<lang>/<slug>.md`, загрузка через `glob()`, frontmatter несёт заголовок, описание и связь с категорией.

**Обоснование**: `glob()` работает с Markdown и генерирует идентификаторы сам. Текст страницы — многоабзацная проза; в JSON она превращается в одну строку с экранированными переводами строк, что делает вычитку и правку неоправданно дорогими. Markdown оставляет текст текстом.

## R6. Словарь интерфейса

**Решение**: TypeScript-модуль с `as const`, а не JSON.

**Обоснование**: официальный рецепт Astro хранит словарь именно так (`recipes/i18n.mdx`), и причина практическая: тип, выведенный из основного языка, делает отсутствующий ключ в другом языке ошибкой компиляции. JSON без дополнительной схемы отдаёт `undefined`, и пропуск обнаруживается только глазами на собранной странице. Встроенного механизма переводов у Astro нет — есть только маршрутизация, — поэтому выбор формата целиком наш.

## R7. Изображения

**Решение**: `astro:assets`, компонент `<Image>` с `priority` для изображения первого экрана; исходники переезжают из `public/assets/` в `src/assets/`.

**Обоснование**: оптимизация применяется только к изображениям, импортированным из исходников; файлы в `public/` копируются как есть. Действующее фоновое изображение подключено CSS-свойством `background-image` (`src/components/Hero.tsx:12`), то есть находится вне досягаемости любой оптимизации. Оно переносится в тег изображения с абсолютным позиционированием и `object-fit: cover` — визуально то же самое, но с генерацией современных форматов, набора размеров и явными размерами против сдвига макета. `priority` помечает изображение первого экрана (подтверждено `reference/modules/astro-assets.mdx`).

**Исключение**: изображение предпросмотра для соцсетей остаётся в `public/` и пережимается один раз вручную. Причина — соцсети требуют постоянный абсолютный адрес, а имена оптимизированных файлов содержат хэш и меняются при каждой пересборке.

## R8. Шрифты

**Решение**: Astro Fonts API, провайдер Google, самостоятельная отдача файлов с домена сайта.

**Обоснование**: в Astro 7 API стабилен — конфигурация на верхнем уровне `defineConfig`, без пометки экспериментальности (`guides/fonts.mdx`). Шрифты скачиваются при сборке, ссылки предзагрузки и метрики запасного шрифта генерируются автоматически. Убирает два сторонних домена из критического пути загрузки, которые сегодня стоят в `index.html:29-31`.

**Проверка при реализации**: наличие кириллического начертания у Playfair Display. Утверждение, что оно есть, взято из общих знаний и не проверено источником — подтверждается рендером украинского заголовка, а не документацией. Если начертания нет, заголовки на кириллице сегодня уже отдаются запасным шрифтом, и это надо обнаружить до публикации, а не после.

## R9. Tailwind

**Решение**: Tailwind 3.4 с действующим `tailwind.config.js` плюс интеграция `@astrojs/tailwind` 6.0.2. Поле `content` расширяется на `.astro`.

**Обоснование и оговорка**: документация Astro прямо описывает эту связку как режим совместимости с третьей версией («Legacy Tailwind 3 support», `guides/styling.mdx`); для четвёртой версии официальный путь другой — плагин `@tailwindcss/vite`. То есть в новый проект сознательно вносится зависимость, помеченная как унаследованная.

Причина, по которой это всё равно верно сейчас: перенос вёрстки проверяется сверкой отображения до и после. Смена мажорной версии Tailwind меняет и набор утилит, и способ конфигурации; выполненная одновременно с переносом, она делает любое расхождение неотносимым к причине — непонятно, ошибка переноса это или изменение движка утилит.

**Рекомендация за пределами этого пакета**: апгрейд до Tailwind 4 запускать сразу после приёмки миграции, отдельным пакетом, где эталоном сверки служат скриншоты, снятые и принятые здесь. Тогда у апгрейда есть проверяемая точка отсчёта, которой сейчас не существует.

**Поправка, внесённая при выполнении Step 1.1**: интеграция `@astrojs/tailwind` не ставится. Её последняя версия 6.0.2 объявляет `peerDependencies: { astro: '^3.0.0 || ^4.0.0 || ^5.0.0' }` — седьмой версии в диапазоне нет, `npm i` останавливается на ERESOLVE. Установка через `--legacy-peer-deps` означала бы взять пакет, который апстрим против этой версии Astro не проверял.

Решение третьей версии Tailwind это не меняет: интеграция делает ровно две вещи — регистрирует плагин PostCSS и подставляет базовый стиль. Первое Vite делает сам по `postcss.config.js`, который в проекте уже лежит; второе даёт `src/index.css`, импортируемый макетом. Набор утилит, конфигурация и палитра — те же, поэтому сверка отображения остаётся осмысленной, ради чего R9 и написан.

**Следствие для Step 7.3**: `postcss.config.js` из списка удаления T058 исключается. Без интеграции он и есть подключение Tailwind; удалённый, он оставит сборку без единой утилиты — и падения не вызовет, страницы просто отрисуются без стилей.

## R10. Интерактив без фреймворка

**Решение**: мобильное меню — `<details>`/`<summary>`; вкладки прайса — скрипт в теге `<script>` компонента, с `role="tablist"`, `aria-selected`, `aria-controls` и обработкой стрелок, Home и End.

**Обоснование**: меню — раскрытие блока, ровно семантика `<details>`, и работает без скриптов и с клавиатуры бесплатно. Вкладки не имеют нативного элемента; вариант на CSS через `:target` меняет адрес страницы и ломает канонический адрес, вариант на скрытых радиокнопках даёт неверную семантику вспомогательным технологиям. Скрипт в компоненте Astro собирается и минифицируется как часть сборки.

**Деградация без скриптов**: вкладки должны отдаваться так, чтобы при отсутствии скриптов были видны все блоки прайса, а не ни одного. Значит начальное состояние разметки — все блоки видимы, а скрытие неактивных выполняет скрипт при инициализации.

## R11. Карта сайта

**Решение**: `@astrojs/sitemap` 3.7.4 с блоком `i18n`; обязателен `site: 'https://lada.kiev.ua'`.

**Обоснование**: интеграция добавляет в карту сайта элементы `xhtml:link` со всеми языковыми альтернативами (подтверждено `guides/integrations-guide/sitemap.mdx`). Важное ограничение: карта сайта — не замена указаниям в разметке страницы. Ссылки на языковые версии и указание версии по умолчанию всё равно проставляются в теле страницы; интеграция их не генерирует.

## R12. Машиночитаемое описание

**Решение**: `HealthAndBeautyBusiness` на главной, `Service` с `OfferCatalog` на страницах категорий, `BreadcrumbList` там же.

**Статус**: типы взяты из общих знаний, источником в этой сессии не подтверждены. Проверяются валидатором структурированных данных до публикации — это дешевле и надёжнее, чем сверка со словарём типов.

**Следствие модели данных**: позиции с долевой ценой («коррекция 50%») в перечень предложений не попадают. Предложение без цены или с нулевой ценой описывает бесплатную услугу, что неверно; отсутствие позиции честнее ложного утверждения.

## R13. Проверки

**Решение**: Playwright для сквозных проверок против собранного сайта, отдельный скрипт сверки полноты контента, `astro check` для типов.

**Обоснование**: проверяемый объект — статический HTML, поэтому все проверки идут против результата сборки, а не против компонентов в изоляции. Модульные тесты компонентов дали бы уверенность в разметке, но не в том, что попало в опубликованный файл, — а требования спеки сформулированы именно про опубликованный файл.

**Механика сверки полноты**: до удаления действующего словаря переводов из него извлекаются все строки контента и сохраняются в фикстуру, разложенную по языкам. Проверка нормализует пробелы и типографские кавычки, после чего ищет каждую строку в HTML соответствующей языковой версии. Фикстура остаётся в репозитории и после миграции: она же ловит потерю блока при любой последующей правке.

## R14. Конфигурация веб-сервера

**Решение**: правило подстановки главной страницы из `.htaccess` удаляется; добавляются `ErrorDocument` на каждый язык, правила кэширования и сжатие.

**Обоснование**: действующее правило (`public/.htaccess:6-10`) отдаёт главную страницу с кодом 200 на любой несуществующий адрес — механика одностраничного приложения, которая после перехода на статические файлы превращает каждый битый адрес в страницу-дубль с кодом успеха. Для статического сайта это чистый вред: поисковик получает бесконечное множество адресов с одинаковым содержимым.

Кэширование разделяется по типу ресурса: файлы сборки в `_astro/` содержат хэш содержимого в имени и кэшируются неизменяемыми надолго, HTML-страницы — на минуты, иначе правка текста не доходит до посетителя.

`ErrorDocument` задаётся отдельно для каталогов `/ru/` и `/en/`, чтобы страница ошибки отвечала на языке раздела.

## R15. Канонический хост и слой доставки контента

**Решение**: канонический хост — `www.lada.kiev.ua`. В конфигурации сайта объявляется он; выкладка завершается сбросом кэша сети доставки контента.

**Обоснование — измерено на действующем сайте 2026-09-06**:

| Запрос | Ответ |
|--------|-------|
| `https://lada.kiev.ua/` | 301 → `https://www.lada.kiev.ua/` |
| `https://www.lada.kiev.ua/` | 200, `cf-cache-status: DYNAMIC`, заголовка кэширования нет |
| `https://www.lada.kiev.ua/assets/logo.jpg` | 200, `cache-control: max-age=14400`, `cf-cache-status: REVALIDATED` |
| `https://www.lada.kiev.ua/nonexistent-path-test-12345` | **200** |
| `https://www.lada.kiev.ua/sitemap.xml` | **200 с HTML главной страницы** |
| `https://www.lada.kiev.ua/robots.txt` | 200, отдаётся сетью доставки контента — в проекте файла нет |
| `/` и `/ru` | побайтово одинаковый ответ |

Три следствия, каждое меняло бы работу, если бы вскрылось позже:

1. **Действующая разметка объявляет неканонический хост.** `index.html:13` и `index.html:16` указывают адреса без `www`, то есть адрес страницы и адрес изображения предпросмотра ведут на перенаправление. Это существующий дефект, а не новое требование; при переносе он устраняется, потому что иначе переносится в новый код.
2. **HTML на стороне сети доставки не кэшируется, статика кэшируется четыре часа.** Значит выкладка HTML видна сразу, а вот замена изображения предпросмотра, файла правил для роботов и карты сайта — постоянных адресов без хэша — до сброса кэша не дойдёт. Файлы сборки с хэшем в имени сбросом не затрагиваются.
3. **Запрос `/sitemap.xml` отвечает успехом и отдаёт HTML.** Это чистая демонстрация вреда подстановки главной страницы: любой служебный адрес выглядит существующим. После миграции по этому адресу окажется настоящая карта сайта, но пока правило подстановки живо, поисковик получает HTML в ответ на запрос XML.

**Отдельно про файл правил для роботов**: сегодня его отдаёт сеть доставки контента своим содержимым, поскольку в проекте файла нет. После добавления собственного надо убедиться, что отдаётся именно он: этот слой умеет дописывать в такой файл собственные строки, и итоговое содержимое может отличаться от того, что лежит в репозитории.

## R16. Аналитика

**Решение**: счётчик переносится в разметку макета без изменений — тот же идентификатор, тот же способ загрузки.

**Обоснование**: после снятия фреймворка счётчик становится самым тяжёлым скриптом страницы, и соблазн отложить его загрузку велик. Но отложенная загрузка теряет визиты посетителей, ушедших в первые секунды, то есть меняет данные, по которым владелец судит о сайте. Изменение поведения аналитики внутри миграции сделало бы несопоставимой статистику до и после — а именно по ней будет оцениваться результат работы.
