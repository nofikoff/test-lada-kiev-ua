# Quickstart: как доказать, что редизайн сделан правильно

Каждый критерий приёмки — команда и ожидаемый результат. Порядок соблюдать: часть проверок идёт против собранного сайта.

## Отправная точка (снять до начала работ)

```bash
npm run build && npm run analyze
```

Ожидается: наибольшая страница — **732 Б** исполняемого кода помимо аналитики. Это и есть порог, с которым сравнивается результат: SC-005 требует «не выросло», а не «уложилось в 5 КБ».

Оценки Lighthouse снимаются на мобильном профиле по трём адресам (`/`, `/ru/`, `/en/`) и записываются рядом. Отправная точка пакета 001: производительность 99/99/100, доступность **96**, поиск 100.

**Визуальный эталон снимается тогда же и здесь же.** Полностраничные снимки трёх языковых версий главной и четырёх страниц категорий уходят в `.playwright-mcp/baseline/`, а перечень невербальных элементов — иконки, ссылки, разделители, подписи — записывается ниже. Без него требование FR-034 («ничего не исчезло») непроверяемо: к моменту финальной сверки старая вёрстка уже перезаписана, и сравнивать будет не с чем.

## Правило прогона: сначала сборка

Каждая проверка идёт против собранного сайта, и `npm run test:e2e` поднимает `astro preview` над содержимым `dist/`. Прогон без предшествующей сборки проверяет **предыдущее** состояние — и выглядит это как необъяснимо зелёная проверка. Поэтому каждая команда ниже и каждый `gate_commands` в `tasks.md` начинаются с `npm run build &&`.

## Правило новых проверок: `test.fixme` до своего шага

Три новые проверки пишутся до реализации и обязаны падать. Чтобы полный прогон не краснел на каждом промежуточном шаге, каждая помечается `test.fixme()`, и пометка снимается ровно в том шаге, где проверка обязана позеленеть — тем же коммитом, что и реализация:

| Проверка | Пометка снимается |
|---|---|
| `contrast.spec.ts`, главная | Step 3.1 |
| `contrast.spec.ts`, прайс | Step 4.1 |
| `contrast.spec.ts`, категории | Step 5.2 |
| `contrast.spec.ts`, шапка и подвал | Step 7.1 |
| `typography.spec.ts` | Step 5.2 |

Шапка и подвал — четвёртая область, а не часть «главной»: они стоят на всех пятнадцати страницах, а пересобираются последними (Step 7.1, T043). Внутри области «главная» их копирайт на 3.82:1 не дал бы T025 позеленить её в Step 3.1 — то есть держал бы под пометкой страницу, которая к тому моменту уже готова.

`reduced-motion.spec.ts` пометки не получает: он пишется и обязан позеленеть внутри одного шага (Step 6.1), а пометка на такой проверке скрывала бы её от гейта собственного шага.

Проверка, оставшаяся под пометкой после своего шага, — это отсутствующая проверка. `npm run test:e2e` покажет её как `fixme`, а не как провал, поэтому искать её нужно глазами в отчёте прогона Step 7.2.

## Полный прогон проверок

```bash
npx playwright install webkit   # один раз на машине и в CI
npm run test:e2e
```

Ожидается: зелёные одиннадцать файлов проверок в трёх проектах прогона (Chromium desktop, Chromium mobile, WebKit).

Восемь унаследованных файлов доказывают, что редизайн ничего не сломал:

| Файл | Что удерживает |
|---|---|
| `content-parity.spec.ts` | весь текст прежней версии на месте (SC-009) |
| `seo-contract.spec.ts` | метаданные, канонические адреса, языковые альтернативы, машиночитаемое описание (SC-010) |
| `routes.spec.ts`, `sitemap.spec.ts` | адреса и карта сайта (SC-010) |
| `interaction.spec.ts` | роли и клавиатура вкладок и меню |
| `no-script.spec.ts` | прайс целиком без скриптов (SC-008) |
| `llms.spec.ts` | описание сайта для машинных читателей |
| `fonts.spec.ts` | шрифты со своего домена, предзагрузка по подмножеству. Единственный унаследованный файл, который работа правит (T007a): он называет гарнитуру заголовков поимённо, и это имя меняется |

Три новых доказывают то, ради чего работа делалась:

| Файл | Критерий | Как меряет |
|---|---|---|
| `contrast.spec.ts` | SC-001, FR-032 | обходит текстовые элементы собранной страницы в трёх состояниях (покой, наведение, фокус), читает вычисленные цвета и считает отношение по WCAG; область — список адресов параметром |
| `typography.spec.ts` | SC-006, FR-031 | `Range.getClientRects()` по абзацу: знаков ÷ строк ≤ 68; там же размер области нажатия вкладок ≥ 24×24 px |
| `reduced-motion.spec.ts` | SC-007, SC-012 | эмуляция предпочтения + отсутствие действующих анимаций + неизменность положений через секунду; там же разбор собранного CSS на порядок вложенности `@supports` — ни один движок прогона отсутствие таймлайна не воспроизводит |

## Оценки Lighthouse

Снять на мобильном профиле по трём адресам после `npm run preview`.

Ожидается: производительность ≥ 95, поиск 100, **доступность 100**. Подъём доступности с 96 до 100 — прямое следствие ухода `white/40` из подвала; если она осталась 96, проверить, не остался ли где-то текст на прежнем уровне прозрачности.

Отдельно выписываются LCP и CLS каждого адреса: SC-004 требует ≤ 2.5 с и < 0.1, а общая оценка производительности их усредняет и остаётся зелёной при провале одной из двух. Сквозной фон и раскрытие первого экрана бьют ровно сюда.

## Ручные проходы

Три вещи не проверяются автоматически и записываются в итоги пакета:

1. **Firefox** (SC-013): открыть главную и одну страницу категории. Ожидается целая страница без проявления блоков и с постоянно плотной шапкой. Собственно перевёрнутую вложенность `@supports` (contracts/motion.md §4) ловит уже `reduced-motion.spec.ts`; этот проход остаётся ради всего остального, что может выглядеть сломанным в третьем движке.
2. **Карта в WebKit** (research.md §R10): проверить, что кадр под фильтром инверсии остаётся интерактивным — перетаскивание и масштабирование работают. При сбое запасной путь согласован: собственная схема со ссылкой.
3. **Темп движения**: пройти главную сверху донизу и убедиться, что движение читается как атмосфера, а не как мельтешение. Эталон — [prototype.html](./prototype.html), открытый рядом.
